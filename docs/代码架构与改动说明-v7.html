三、固件代码架构

我们的代码只加在板级这一层，不侵入上游逻辑——方便以后跟进上游升级。

板级目录如何被编译

main/CMakeLists.txt 用 glob 收录板级目录所有源码，新模块放进 boards/ai-dog-s3/ 就自动参与编译，无需改 SOURCES 列表：

# main/CMakeLists.txt:936
file(GLOB BOARD_SOURCES
    ${CMAKE_CURRENT_SOURCE_DIR}/boards/${BOARD_DIR}/*.cc
    ${CMAKE_CURRENT_SOURCE_DIR}/boards/${BOARD_DIR}/*.c
)

板级选择由 Kconfig 驱动：firmware/config/ai-dog-s3.defaults 中一行 CONFIG_BOARD_TYPE_AI_DOG_S3=y，经 SDKCONFIG_DEFAULTS 注入构建。

Android 端架构

组件职责
MainActivity状态面板（在线/模式/电量/Wi-Fi/故障）、四模式切换、红色急停按钮
SetupActivity设备 IP 设置（SharedPreferences）、Wi-Fi 凭据下发
DeviceApiOkHttp 封装 4 个 HTTP 接口 + WebSocket 推送，WS 失败自动降级 2 秒轮询
DeviceStatusGson 模型，字段与设备端 JSON 一一对应

技术栈 Java + XML/ViewBinding（不用 Kotlin/Compose），AGP 8.7.3 + Gradle 8.13 + JDK 21，compileSdk 36 / minSdk 26。

十、改动流程（后续必须遵守）

  1. 先澄清再动手：需求不清先问清关键决策，不猜测。
  2. 确认落点：只动 boards/ai-dog-s3/ 与 android/，不侵入上游。
  3. 写代码：中文注释写"为什么"；安全逻辑（急停、互斥）显式写清。
  4. 编译验证：看到真实产物（xiaozhi.bin / app-debug.apk）才算过，禁止"应该能编过"。
  5. 提交 git：固件仓库一条改动一次提交。
  6. 更新文档与记忆：同步 docs/ 与 .workbuddy-ai/memory/。
  7. 本文档版本化更新：改动发生后新建版本文件（如 v3），在图中把新改动用绿框标出，并在"修改历史"登记。

13.2 刻意保留、不做"精简"的三处

项为什么保留
RecyclerView / ConstraintLayout 显式版本约束Material 的传递依赖会引入更旧版本，删掉直接声明后离线构建会解析失败（v4 已验证）
三层停车保护（App 松手发 stop / 单条在途不堆积 / 设备端看门狗）安全冗余不能为了"代码更短"削减
状态 setter（SetMoving / SetBatteryPercent / SetCharging）电池采样与运动模块的接入点，硬件到位即调用；属预留接口不是死代码

15.1 为什么撤（问题怎么被发现的）

用户在确认面包板接线时问了一句"TCRT 插在面包板上，还能照到地板上吗"——这一问直接推翻元件 4 的可行性：

维度实际约束后果
传感器朝向TCRT5000 模块的发射/接收头在 PCB 正面，插进面包板后镜头朝上（朝天花板）被测地面在模块背后，根本照不到
有效量程0.2–15mm（典型工作距 5–10mm）面包板厚 9mm + 狗底盘离地几十 mm，双重超程
裸装件折弯三脚 TCRT 直插也是头朝上，要朝下必须折脚 180°反复折弯会断，不可靠
结论：这不是"调一下参数就能用"的问题，而是安装形态与测量原理冲突。真要做巡迹，必须把探头做成独立朝下的小板挂底盘前缘（离地 5–10mm），5 根杜邦线回主控——面包板继续当大脑，探头不上面包板。

15.3 前后对比：从"扫地面"到"看桌沿"

这条改动的教训："编译通过 + 校验通过"不等于"能装上"。几何/朝向约束必须在设计阶段就用实物形态去核（谁朝哪、离被测面多远），否则整块图纸都会白画。以后每加一个元件，先问三件事：镜头朝哪、离被测目标多远、有没有东西挡光路。
