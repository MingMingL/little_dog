二、固件代码架构

xiaozhi-esp32 的分层很清晰，我们的代码只加在板级这一层，没有侵入上游逻辑——这是刻意的选择，方便以后跟进上游升级。

关键机制：板级目录如何被编译

main/CMakeLists.txt 用 glob 收录板级目录所有 *.cc/*.c，所以新增模块放进 boards/ai-dog-s3/ 就会自动参与编译，不需要改 SOURCES 列表：

# main/CMakeLists.txt:936
file(GLOB BOARD_SOURCES
    ${CMAKE_CURRENT_SOURCE_DIR}/boards/${BOARD_DIR}/*.cc
    ${CMAKE_CURRENT_SOURCE_DIR}/boards/${BOARD_DIR}/*.c
)

板级选择则由 Kconfig 驱动：firmware/config/ai-dog-s3.defaults 里的一行 CONFIG_BOARD_TYPE_AI_DOG_S3=y，通过 SDKCONFIG_DEFAULTS 注入构建。

三、Android 端架构

MainActivity

状态面板（在线/模式/电量/Wi-Fi/故障）、四模式切换、红色急停按钮

SetupActivity

设备 IP 设置（SharedPreferences）、Wi-Fi 凭据下发

DeviceApi

OkHttp 封装：4 个 HTTP 接口 + WebSocket 推送，WS 失败自动降级 2 秒轮询

DeviceStatus

Gson 模型，字段与设备端 JSON 一一对应

技术栈为 Java + XML/ViewBinding（不用 Kotlin/Compose），AGP 8.7.3 + Gradle 8.13 + JDK 21，compileSdk 36 / minSdk 26。

对比 3 · 启动流程：控制服务何时启停

改动前（若直接常开服务）
  • 开机即启动 HTTP 服务
  • 未配网时进入配网热点
  • 热点 captive portal 也占 80 端口
  • → 配网页打不开 / 服务启动失败
改动后（绑网络事件）
  • STA 连上路由器 → Start()
  • 进入配网热点 → Stop() 让出端口
  • Wi-Fi 断开 → 上报故障给 App
  • → 两条路径互不冲突

实现方式是包装而非覆盖 SetNetworkEventCallback：先处理控制服务启停，再把事件原样转发给上层 Application，不破坏上游行为。

六、后续改动必须遵守的流程

  1. 先澄清再动手。需求不清、有多个合理方案时，先问清关键决策项（通信方式、技术栈、范围），再写代码。
  2. 确认改动落点。优先只动"我们自己的目录"（boards/ai-dog-s3/、android/），不侵入上游 xiaozhi-esp32 逻辑，便于跟进升级。
  3. 写代码。注释用中文说明"为什么这么做"，尤其是绕过坑的地方；安全相关逻辑（急停、互斥）必须显式写清。
  4. 编译验证，不靠推测。固件跑 .\build-ai-dog.ps1（非沙箱模式）；Android 用 JDK 21 跑 gradlew assembleDebug。必须看到真实产物（xiaozhi.bin / app-debug.apk）才算通过，不得以"应该能编过"结案。
  5. 提交 git。固件仓库 firmware/xiaozhi-esp32，一条改动一次提交，信息写清做了什么。
  6. 更新文档与记忆。同步 docs/ 下对应文档；把本次决策、坑、结论追加到 .workbuddy-ai/memory/YYYY-MM-DD.md。
  7. 更新本文件的图文对比。新增/修改代码后，在"改动清单"补行、在"前后对比"补图，让这份文档始终反映当前真实状态。
这条流程已写入项目长期记忆（.workbuddy-ai/memory/MEMORY.md），后续会话会自动遵守。
