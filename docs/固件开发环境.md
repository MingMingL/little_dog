# 机器狗 V1 固件开发环境说明

> 状态：**首次编译已通过**（2026-10-14），产物 `build/xiaozhi.bin`（2,132,880 字节），板卡 `ai-dog-s3` 已生效；**尚未在真实硬件上验证**（主控仍在途中）。
> 本文所有引脚与命令以 `firmware/xiaozhi-esp32` 工作副本为准。

## 1. 技术选型

语音聊天直接采用开源项目 [xiaozhi-esp32](https://github.com/78/xiaozhi-esp32)（MIT 许可）作为设备端语音栈，不自己实现传输、编解码与打断逻辑。

已确认的关键事实（来自项目 README）：

- 支持 ESP32-S3，通信为 **WebSocket** 或 **MQTT + UDP**，音频为 **Opus**；
- 支持传统 **ASR → LLM → TTS** 级联，也支持 Realtime 端到端语音模型；
- 离线唤醒基于乐鑫 **ESP-SR**，支持自定义唤醒词；具备 AEC 硬件时可全双工；
- 服务端可选官方云 **xiaozhi.me**（本次先用它打通链路），或自建 Python/Java/Go 服务端；
- 构建要求 **ESP-IDF v6.0.1+（推荐 v6.1）**，**不再支持 IDF 5.x**。

### 两个已踩的坑

1. **不要运行 `install.ps1`**：本机会报 `Start-Process : 已添加项。字典中的关键字:"http_proxy"...`，原因是环境变量里同时存在 `http_proxy` 与 `HTTP_PROXY`（大小写重复键），PowerShell `Start-Process` 会抛异常。工具链本来就已装好，无需再装。
2. **工具链在 `C:\Espressif\tools`，不在 `C:\Users\<你>\.espressif`**。误跑过一次 `idf_tools.py install` 会在 `C:\Users\lmmmm\.espressif` 留下不完整下载（只有 gdb 相关），可安全删除。

## 4. 板级配置 `ai-dog-s3`

为什么不用现成配置：xiaozhi 对 ESP32-S3 的**默认板级是 `bread-compact-wifi`（面包板精简 WiFi）**，但它假设接了 SSD1306 OLED；我们没有买屏幕，直接编译会在启动时报显示初始化错误。因此新增 `ai-dog-s3`：

- `GetDisplay()` 返回 `NoDisplay()`；
- `GetLed()` 返回 `NoLed`（官方 DevKitC-1 的 GPIO48 是 WS2812，首版先不驱动）；
- 音频引脚沿用官方面包板方案，方便照图接线；
- BOOT 键（GPIO0）：未配网进配网，已配网切换语音对话（对应 PRD **FR-17**）。

### 引脚分配

| 功能 | GPIO | 备注 |
|---|---|---|
| INMP441 WS / SCK / SD | 4 / 5 / 6 | I²S 麦克风输入 |
| MAX98357A DIN / BCLK / LRC | 7 / 15 / 16 | I²S 功放输出 |
| BOOT 按键 | 0 | 配网 / 切换对话 |
| I²C SDA / SCL | 41 / 42 | 给 VL53L0X 测距（屏幕未用） |
| 电池电压采样 | 8 | ADC，需分压后接入 |

> 电机、巡线、看门相关引脚**首版固件尚未初始化**，仅先占位。

## 5. 构建与烧录

```powershell
cd F:\software\workbuddy\AI-Dog\firmware
.\build-ai-dog.ps1                              # 编译
.\build-ai-dog.ps1 -Action flash -Port COM3     # 烧录（按实际串口改）
.\build-ai-dog.ps1 -Action monitor -Port COM3   # 看日志
.\build-ai-dog.ps1 -Action menuconfig           # 改配置
```

脚本里已固化下面 5 项环境修正（**别删**，删了就会复现首次编译时那串报错）：

1. `IDF_COMPONENT_CACHE_PATH` → 工作区：组件管理器默认往 `%LOCALAPPDATA%\Espressif\ComponentManager\Cache` 解压，会被拒写。变量名必须是 `IDF_COMPONENT_CACHE_PATH`（前缀 + `CACHE_PATH` 字段），写成 `IDF_COMPONENT_CACHE` 会静默失效。
2. `CODEBUDDY_SAFE_DELETE_ENABLED=0`：cmake 配置阶段会批量删临时文件，超过 50 个文件即被保护机制 fail-closed 拦截，configure 直接失败。
3. `TMP/TEMP` → `firmware/.build-tmp`：`gcc`/`as` 的临时文件默认在系统 Temp，编译到一半会被拒。
4. `CCACHE_DISABLE=1`：ccache 的临时目录同样会被拒；首次编译本来也用不上缓存。
5. 重配置时加 `-DCMAKE_NINJA_FORCE_RESPONSE_FILE=1`：链接 `xiaozhi.elf` 前的编译命令有上百个 `-I`，会撞 Windows 命令行 32767 字符上限报 `CreateProcess: The parameter is incorrect`。CMake 打印的 "变量未被使用" 是误报，`build.ninja` 里确实生成了 `RSP_FILE`。

其它经验：构建需在**非沙箱模式**下跑（沙箱会在编译到第 1000 个目标左右开始拒绝 .obj 写入）；失败后续跑 `ninja -C build all` 是增量的，不要删 `build/` 重来；`.ps1` 脚本保持 ASCII（PowerShell 5.1 按 GBK 读无 BOM 文件，中文注释会破坏解析）。
