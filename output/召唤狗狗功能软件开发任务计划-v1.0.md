## 2. 开发策略与规范

1. **分支**：`feature/summon-v15`，每个 SW 任务一个 commit，信息带任务号（如 `SW-102: 4-mic I2S capture backend (a)`）。
2. **编译开关**：`CONFIG_AI_DOG_ENABLE_SUMMON`，**默认 OFF**——任何时刻都能构建出与 V1 行为一致的固件，召唤代码不影响 V1 验收。
3. **参数化**：方案 §4.3 全部参数进 Kconfig / `config.h`，禁止硬编码；标定后冻结值回写方案文档。
4. **日志规范**：TAG 用 `summon` / `doa` / `mic_array` / `vision` / `line_i2c`；每个决策点输出依据（DOA 角度、能量、子状态、与阈值的对比）——延续"输出完整 prompt"的调试习惯；不输出敏感信息。
5. **代码落点与风格**：全部落在 `main/boards/ai-dog-s3/`，沿用现有 `ai_dog_*` 单例 + 回调风格，与 `ai_dog_control` 状态机对接，不新增全局线程模型。
6. **仿真先行**：`tools/sim_dog.py` 先扩展为 Summon 状态机仿真，硬件未到也能验证抢占/超时/降级逻辑。

## 6. 与风险表的联动

开发中触发下列任一降级条件时，按最终实施方案 §7（R-F1~R-F10）执行，并在 SW-403 记录：

- R-F1（自噪）→ SW-104 的 30% 占空比档 + SW-105 的 NSNet2 辅助；

### 仿真固化的两个状态机缺陷（SW-004 产出，已修复）

1. **S5 重搜无限循环**：视觉连续失败 → S5 → 命中 → S2 → 再失败 → S5……没有退出条件。
   修复：每次召唤最多 2 次 S5（`rescan_count_`），第 2 次仍找不到一律回 Idle。
2. **重搜阶段被总时限反复打回**：进入 Rescanning 后总时限检查每个 tick 都成立，
   反复 `continue` 导致 `DoRescan()` 永远得不到执行（死锁在原地）。
   修复：总时限分支加 `phase != Rescanning` 条件。

### 构建环境坑（已固化到脚本，避免重复踩坑）

1. **Windows 命令行超长**：工作区路径长 + IDF 巨量 `-DESP_LCD_*_VER_*` 宏定义 →
   `ninja: fatal: CreateProcess` 。解：`-DCMAKE_NINJA_FORCE_RESPONSE_FILE=ON`。
2. **ccache 假死**：两个 gcc 共享同一个 `ccache/tmp/cmd_args.tmp.*` 响应文件，
   CPU 0% 无子进程永久卡住（会误以为是“大文件编译慢”）。
   解：`IDF_CCACHE_ENABLE=0`（单用 `CCACHE_DISABLE=1` 不够，launcher 仍是 ccache）。
3. **半成品 build 目录**：`set-target` 失败后的残留 `build/` 没有 CMakeCache.txt，
   fullclean 拒绝删除并报“doesn't seem to be a CMake build directory”。解：先手动删。
4. **组件缓存为空**：configure 阶段会重下载 760 MB（卡 1 小时+）；先从共享仓拷缓存。
